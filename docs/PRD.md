# 0. 给 AI 编程助手的最高优先级指令

你是本项目的产品技术负责人、全栈工程师和测试助手。你需要帮助一位编程初学者，从现有项目开始，一步一步开发出可运行、可测试、可部署的产品。

必须遵守以下规则：

1. **先检查，再修改。** 开始前检查当前目录、项目文件、`package.json`、环境配置、Git 状态和已有代码。不要假定项目为空。
2. **分阶段开发。** 不要一次性实现整份文档。每次只完成一个明确、可验证的小阶段。
3. **先说明计划。** 开始每个阶段时，用简体中文说明目标、涉及文件、实施步骤、风险和验证方法，然后再操作。
4. **不虚报。** 只有实际运行过的命令、测试和构建才可以报告为成功。未执行的检查必须明确标注。
5. **面向初学者。** 采用容易理解、维护和调试的实现方式；不引入不必要的复杂架构和依赖。
6. **不擅自扩展需求。** 不添加本文档没有要求的大型功能。遇到关键歧义先询问；非关键细节采用文档定义的默认方案。
7. **保护已有成果。** 修改前检查现有实现；不要随意删除或覆盖正常功能。重大改动前说明原因。
8. **修改后验证。** 根据项目实际配置运行 lint、类型检查、单元测试、集成测试或构建，并修复本次改动引入的问题。
9. **开发者沟通使用简体中文。** 面向用户的网站 UI 默认使用简体中文。英语训练内容使用自然、易懂的英语；纠错解释可根据用户设置使用中文或英语。
10. **每次只要求用户完成必要操作。** 需要安装软件、注册服务、输入密钥、执行命令或手动测试时，提供逐步操作指引和预期结果。
11. **API 密钥只能放服务端。** DeepSeek API Key 不得写进前端代码、浏览器可访问的变量、客户端构建产物、公开仓库或提交到 Git。使用服务端环境变量，并提供 `.env.example`，其中只能包含变量名和示例占位符。
12. **采用 API-first 架构。** 核心业务逻辑、AI 调用、学习分析和数据访问放在服务端。网站前端与未来 App 都通过受保护的后端 API 访问核心业务。
13. **数据库必须真实接入。** 不得只使用浏览器 `localStorage` 冒充正式数据库。可在 UI 阶段使用明确标注的 mock 数据，但正式功能必须接入真实数据库。
14. **学习进度需要数据驱动。** 个性化学习必须基于用户实际练习记录、错误类型、完成情况和趋势，不得随机生成进步结果或虚构学习数据。
15. **不要假设 DeepSeek 提供完整语音链路。** 本项目使用 DeepSeek API 处理文本对话、语言反馈和学习建议。语音识别（STT）和语音合成（TTS）需要独立选型，并封装为可替换的服务接口。
16. **不伪造 AI 能力。** 缺少 API Key、网络不可用或接口报错时，应显示清楚的错误提示。开发时可提供标记明确的模拟模式，但不得将模拟回复称为真实 DeepSeek 结果。
17. **隐私和安全优先。** 不记录密钥；日志中避免保存不必要的完整对话和个人信息。保护用户数据的读取、修改和删除权限。
18. **Sealos DevBox 使用前先确认。** 项目计划使用 Sealos DevBox 作为开发环境，并使用 Sealos 作为部署平台。开始开发前核实当前账号、项目环境、资源配置和可用部署方式。不要假定 DevBox 与部署环境的配置会自动同步；部署时需要独立配置生产环境变量、数据库连接和网络访问。若当前环境不支持某项功能，应说明原因并提出兼容方案。
19. **每阶段结束必须汇报。** 用简体中文列出完成内容、修改文件、实际执行的验证、未解决问题和下一步建议。除非用户明确要求继续，不要自动跨越多个大型阶段。

# 1. 产品概述

## 1.1 产品定位

SpeakMate AI 是一款以 AI 为口语陪练的英语口语训练产品。用户可以选择通用口语或考试口语训练，与 AI 进行英语对话，并获得纠错、复习和个性化训练建议。

第一阶段先开发 Web 网站，但从一开始就采用 **API-first、前后端职责分离、数据库持久化** 的设计，为未来开发 iOS / Android App 预留接口。

## 1.2 产品核心目标

1. 让用户能持续与 AI 进行英语口语练习。
2. 提供通用口语与 IELTS / TOEFL 口语训练。
3. 根据用户真实的练习记录识别常见错误和薄弱点。
4. 根据用户学习目标、练习表现和进步趋势动态调整后续训练内容与难度。
5. 通过数据库保存学习过程，使用户更换设备或以后使用 App 时仍能访问自己的学习记录。
6. 为未来增加更多学习模块保留可扩展性，但第一期只实现口语训练。

## 1.3 产品原则

- **AI 口语训练优先：** 产品重点是与 AI 练习口语，不是传统课程内容平台。
- **数据驱动：** 所有进步结果都应能追溯到实际练习数据。
- **渐进开发：** 先完成可靠的核心流程，再逐步增加功能。
- **接口优先：** Web 和未来 App 共用后端业务接口。
- **服务可替换：** AI 模型、语音识别、语音合成和数据库访问层应避免与 UI 强耦合。
- **诚实反馈：** AI 的评估属于辅助性学习反馈，不应冒充官方 IELTS / TOEFL 分数或专业考试评分结果。

# 2. 用户与使用场景

## 2.1 目标用户

- 希望提升日常英语口语的学习者。
- 希望练习 IELTS 口语的学习者。
- 希望练习 TOEFL 口语的学习者。
- 希望根据个人错误与学习进度获得个性化训练的用户。

## 2.2 核心使用流程

1. 用户打开网站并进入口语训练。
2. 用户选择「通用口语」或「考试口语」。
3. 用户选择场景、难度或考试类型。
4. 用户开始与 AI 进行口语对话。
5. 系统记录用户输入、AI 回复、练习时间和反馈。
6. AI 根据对话生成纠错与学习建议。
7. 系统将练习结果保存到数据库。
8. 学习分析模块更新用户的错误统计、能力趋势和待复习内容。
9. 下次用户进入练习时，系统根据历史数据推荐训练内容或调整难度。
10. 用户可以查看自己的学习历史与阶段变化。

# 3. 第一阶段产品范围

## 3.1 第一阶段必须实现

### A. 口语训练首页
- 显示产品名称和简要说明。
- 提供两个清晰入口：
  - 通用口语
  - IELTS / TOEFL 口语训练
- 显示开始练习的主要按钮。
- 页面应支持桌面和移动浏览器。

### B. 通用口语训练
- 用户选择或输入日常练习主题。
- 提供预设场景，例如：
  - 日常生活
  - 自我介绍
  - 餐厅点餐
  - 酒店入住
  - 购物
  - 旅行
  - 学习与工作
  - 求职面试
  - 自由对话
- 用户可以选择初级、中级或高级难度。
- AI 作为自然、耐心的英语对话伙伴。
- AI 应尽量一次提出一个主要问题，避免同时抛出多个问题。
- AI 应根据用户的回答继续对话，而不是只给出固定答案。
- 用户可以结束练习并查看总结。

### C. IELTS / TOEFL 口语训练
- 用户先选择考试类型：IELTS 或 TOEFL。
- 用户选择练习任务或题型。
- AI 按照所选考试的练习目标与流程进行训练。
- IELTS 可按 Part 1、Part 2、Part 3 的训练形式组织练习。
- TOEFL 应按项目实际确认的当前考试题型和训练要求组织练习；不得未经核实就把旧版考试格式当作当前标准。
- 支持模拟答题、反馈和练习总结。
- 反馈必须标明是 AI 辅助学习建议，不是官方考试分数或官方评分。

### D. AI 文本对话能力
- 后端接入 DeepSeek API。
- 系统提示词根据训练模式、难度、语言偏好和本次目标动态生成。
- AI 需要理解上下文并维持当前练习主题。
- 支持对话失败、超时、限流和服务不可用时的错误处理。
- API Key 只在服务端使用。

### E. 语音交互
- 用户可以使用麦克风提交英语语音。
- 系统将语音转成文本后交给对话服务。
- AI 回复可以显示为文字，并在启用语音合成后朗读。
- 用户可以在权限允许的情况下暂停或结束语音练习。
- 页面需提示麦克风权限状态、录音状态和服务错误。
- STT / TTS 服务需封装成独立模块，以便未来替换供应商。
- 如果第一阶段尚未完成真实语音服务，必须明确说明当前版本只支持文本，不能把假按钮显示成已可用语音功能。

### F. 对话中的语言反馈
- 识别语法问题。
- 提供更自然的英语表达。
- 指出重要词汇或搭配问题。
- 解释错误原因。
- 提供正确例句。
- 可设置即时反馈或练习结束后统一反馈。
- 默认不要在每轮对话中长篇讲解，以免打断口语练习；优先维持对话，再在适当时机反馈。

### G. 练习总结
每次练习结束后生成总结，至少包括：
- 本次练习主题与模式。
- 练习时长。
- 用户实际完成的轮次。
- 用户表达中值得保留的优点。
- 重点错误及正确表达。
- 值得学习的词汇或短语。
- 下一次建议练习的重点。
- 如果没有足够数据，应明确显示「数据不足」，不得编造统计或分数。

### H. 用户与学习数据
- 提供用户注册、登录和退出能力。
- 学习记录关联到正确的用户。
- 用户可以查看历史练习。
- 用户可以查看常见错误与学习趋势。
- 用户可以删除自己的练习记录。
- 不同用户的数据必须严格隔离。

## 3.2 第一阶段暂不实现

除非用户明确要求，否则暂不开发：
- 词汇、阅读、写作、听力等独立学习板块。
- 社区、好友、排行榜。
- 直播课程和真人教师。
- 付费订阅、支付和积分商城。
- 复杂的多 Agent 协作系统。
- 原生 iOS / Android App。
- 未经数据支持的自动能力评分。
- 大规模内容管理后台。

# 4. 两个口语板块的详细需求

## 4.1 板块一：通用口语

### 目标

帮助用户练习日常英语交流，提高表达自然度、回答完整度和对话流畅性。

### 进入流程

1. 用户点击「通用口语」。
2. 选择主题或场景。
3. 选择难度：初级 / 中级 / 高级。
4. 选择反馈偏好：
   - 对话优先，结束后统一纠错（默认）。
   - 每轮简短纠错。
5. 开始对话。

### AI 行为要求

- 根据用户水平使用适当的词汇和句子长度。
- 以自然、日常的英语交流为主。
- 一次主要问一个问题。
- 根据用户实际回答继续交流。
- 用户表达错误时，避免羞辱或过度打断。
- 当用户需要帮助时，可提供更自然的表达。
- 对话结束后给出结构化总结。
- 不把普通聊天伪装成正式考试评分。

## 4.2 板块二：IELTS / TOEFL 口语训练

### 目标

帮助用户熟悉考试口语任务、组织答案并根据反馈改进表达。

### 进入流程

1. 用户点击「IELTS / TOEFL 口语训练」。
2. 选择 IELTS 或 TOEFL。
3. 选择题型或练习任务。
4. 选择练习模式：
   - 练习模式：允许提示与指导。
   - 模拟模式：尽量按指定流程进行，结束后统一反馈。
5. 开始训练。
6. 结束后查看分析结果。

### IELTS 训练

- 支持 Part 1 日常问答练习。
- 支持 Part 2 个人陈述练习。
- 支持 Part 3 深入讨论练习。
- 题目、流程和反馈应与所选 Part 匹配。
- 可以从用户答案中分析表达相关的学习问题，例如语法、词汇、连贯性和回答展开情况。
- 如显示参考等级或分数估计，必须标明是 AI 估计，仅用于学习参考，不保证与真实考试评分一致。

### TOEFL 训练

- 题型和训练流程必须基于开发时核实的当前 TOEFL 官方考试信息。
- 将题型与评分维度设计为可配置数据，避免题型更新后需要重写整个业务逻辑。
- 不要在未核实当前考试要求前硬编码题型数量、时间或评分规则。
- 任何分数估计均需明确标记为 AI 辅助估计。

# 5. AI 与 DeepSeek API 需求

## 5.1 DeepSeek 的职责

DeepSeek API 在本项目中负责：
- 生成口语对话回复。
- 理解用户回答与对话上下文。
- 根据用户表达生成纠错反馈。
- 生成练习总结。
- 提出下一次训练建议。
- 根据历史学习数据辅助生成个性化训练计划。

## 5.2 服务端调用原则

- 只能由服务端调用 DeepSeek API。
- API Key 从环境变量读取，例如 `DEEPSEEK_API_KEY`。
- 禁止在前端代码中直接调用需要长期密钥的接口。
- 不得将密钥提交到 Git。
- API 请求需设置合理的超时、错误处理和必要的日志。
- 需要支持模型名称通过环境变量或服务端配置调整，避免在多个文件中写死。
- 不要把用户的完整历史记录无差别地发送给模型；只提供完成当前任务所需的相关上下文和学习摘要。

## 5.3 AI 服务抽象

建立统一的服务层，例如：
- `ConversationService`：处理对话流程。
- `FeedbackService`：生成语言反馈。
- `SessionSummaryService`：生成练习总结。
- `LearningPlanService`：提出个性化练习建议。
- `DeepSeekProvider`：封装 DeepSeek API 的具体调用。

命名可根据项目现有结构调整，但职责应保持清楚。前端组件不能直接依赖 DeepSeek SDK 或 API 密钥。

## 5.4 AI 输出结构

对于需要写入数据库的反馈，优先要求模型返回经过验证的 JSON 数据，例如：

```json
{
  "corrections": [
    {
      "original": "Yesterday I go shopping.",
      "corrected": "Yesterday, I went shopping.",
      "category": "grammar",
      "explanation": "Use the past tense because the action happened yesterday."
    }
  ],
  "useful_phrases": [
    {
      "phrase": "go shopping",
      "meaning_zh": "去购物",
      "example": "I usually go shopping on weekends."
    }
  ],
  "strengths": [
    "The main idea was clear."
  ],
  "next_practice_focus": [
    "Practice talking about past events."
  ]
}
```

要求：
- 以上仅为结构示例，不是固定答案。
- 对模型返回值进行 schema 校验。
- 如果 JSON 无效，应进行有限的恢复或返回可理解的错误，不得直接把无效数据写入数据库。
- 不能把模型没有提供的字段随意伪造为真实结果。
- 反馈应尽量引用用户本次实际说过的内容。

# 6. 语音系统需求

## 6.1 语音链路

目标流程：

1. 浏览器请求麦克风权限。
2. 用户开始说话。
3. STT 服务把语音转换成文本。
4. 服务端将文本和必要的会话上下文交给对话服务。
5. DeepSeek 生成英语回复。
6. 前端显示用户文本和 AI 回复。
7. TTS 服务将 AI 回复转换成语音并播放（若已配置）。
8. 对话内容和必要的会话数据保存到数据库。

## 6.2 服务抽象

至少为以下能力定义独立接口：
- `SpeechToTextProvider`
- `TextToSpeechProvider`

具体供应商、浏览器原生能力或云服务在技术验证后确定。供应商不应被硬编码进 UI。

## 6.3 语音交互状态

界面至少能区分：
- 空闲。
- 正在请求麦克风权限。
- 正在录音。
- 正在识别语音。
- 正在等待 AI 回复。
- 正在播放 AI 语音。
- 发生错误。
- 练习已结束。

必须防止用户连续点击造成重复请求、重复保存或会话状态混乱。

## 6.4 兼容性

- 第一阶段优先支持当前主流桌面和移动浏览器。
- 明确提示浏览器对麦克风和语音能力的支持差异。
- 未来 App 应可以使用原生录音能力，并继续调用同一套后端业务 API。
- 不要假设浏览器原生语音识别在所有操作系统、浏览器和地区都可用。

# 7. 数据库与数据模型

## 7.1 数据库目标

数据库不是可选的装饰功能。它用于保存真实学习历史，并支持个性化学习和跨设备使用。

建议使用 PostgreSQL。可以优先评估 Supabase 等托管 PostgreSQL 服务，但在正式选定前需要核实账号可用性、网络、价格和部署环境。

## 7.2 初步数据表

实际表名和字段可根据实现调整，但必须覆盖以下业务实体。

### `profiles` — 用户资料

字段建议：
- `id`：关联认证用户 ID。
- `display_name`：显示名称。
- `english_level`：用户自评英语水平。
- `learning_goal`：学习目标，例如日常口语、IELTS 或 TOEFL。
- `preferred_feedback_language`：偏好的反馈语言。
- `created_at`、`updated_at`。

### `practice_sessions` — 练习会话

字段建议：
- `id`：会话 ID。
- `user_id`：所属用户。
- `mode`：`general` 或 `exam`。
- `exam_type`：`ielts`、`toefl` 或空。
- `topic`：主题或场景。
- `difficulty`：难度。
- `feedback_mode`：即时反馈或结束后反馈。
- `started_at`、`ended_at`。
- `duration_seconds`：实际时长。
- `status`：进行中、已完成或失败。
- `created_at`。

### `conversation_messages` — 对话消息

字段建议：
- `id`。
- `session_id`。
- `user_id`。
- `role`：`user` 或 `assistant`。
- `content_text`：消息文本。
- `sequence_number`：会话内顺序。
- `created_at`。
- 可选的 `metadata`：仅存储必要的非敏感结构化信息。

默认不长期保存原始音频文件。若未来确实需要保存音频，必须先明确用途、保留期限、用户同意和删除方式。

### `language_feedback` — 语言反馈

字段建议：
- `id`。
- `user_id`。
- `session_id`。
- `message_id`：关联被分析的用户消息（如适用）。
- `category`：语法、词汇、搭配、流畅度相关建议等。
- `original_text`。
- `corrected_text`。
- `explanation`。
- `severity` 或 `priority`（可选）。
- `created_at`。

### `session_summaries` — 练习总结

字段建议：
- `id`。
- `user_id`。
- `session_id`。
- `strengths`。
- `key_errors`。
- `useful_phrases`。
- `next_practice_focus`。
- `data_confidence` 或数据充分性标记。
- `created_at`。

复杂结构可以使用 PostgreSQL JSONB，但需要在应用层验证数据结构。

### `learning_profiles` — 学习状态

字段建议：
- `user_id`。
- `current_focus`：当前主要训练重点。
- `estimated_level`：内部辅助估计，不是官方分数。
- `level_confidence`：估计可信程度或数据充分性。
- `updated_at`。

### `skill_metrics` — 学习指标快照

字段建议：
- `id`。
- `user_id`。
- `skill_key`：例如 `past_tense`、`article_usage`、`vocabulary_range`。
- `metric_value`：明确计算口径的数值或等级。
- `sample_count`：样本量。
- `period_start`、`period_end`。
- `created_at`。

### `review_items` — 待复习内容

字段建议：
- `id`。
- `user_id`。
- `source_feedback_id`。
- `item_type`。
- `prompt`。
- `expected_answer`。
- `status`：待复习、已掌握、稍后复习。
- `due_at`。
- `created_at`、`updated_at`。

## 7.3 数据安全要求

- 所有用户相关数据都必须与认证用户 ID 关联。
- 服务端每次读取或修改数据时必须检查用户权限。
- 若使用 Supabase，应配置并测试 Row Level Security（RLS）。
- 普通用户不能读取、修改或删除其他用户的数据。
- 不允许仅依靠前端传入的 `user_id` 判断数据所有权。
- 提供删除练习记录的服务端能力。
- 避免在日志中保存 API Key、认证令牌或不必要的完整对话。
- 为数据库变更保留可追踪的迁移文件。
- 对数据库访问失败提供可理解的错误提示。

# 8. 个性化学习与自动调整机制

## 8.1 产品目标

系统根据用户实际学习情况动态调整后续训练，而不是对每个用户一直提供同样的题目。

系统应能逐渐回答：
- 用户最常犯什么错误？
- 哪些错误已经减少？
- 哪些问题仍然反复出现？
- 用户最近的练习是否更稳定？
- 接下来应该练什么？
- 是否应该保持、降低或提高练习难度？

## 8.2 学习数据来源

个性化判断只能使用实际数据，例如：
- 用户真实完成的练习会话。
- 用户实际提交的文本或语音识别结果。
- AI 针对实际表达生成并经过结构校验的反馈。
- 用户是否完成了复习题。
- 同一类错误在不同练习中的出现次数和变化。
- 用户明确设置的学习目标、英语水平和反馈偏好。

不得将单次 AI 判断直接视为准确的长期能力结论。

## 8.3 学习调整流程

每次练习完成后：

1. 保存本次会话和对话记录。
2. 生成本次语言反馈和总结。
3. 从反馈中提取结构化的错误类别和训练重点。
4. 更新用户的错误统计和学习指标。
5. 对比历史数据，判断哪些问题反复出现或有所改善。
6. 生成下一次练习建议。
7. 在用户下次进入训练时展示建议，并根据产品规则预选或调整练习内容。
8. 用户可以接受建议，也可以自行选择其他主题或难度。

## 8.4 第一版推荐策略

第一版优先采用 **可解释的规则 + AI 生成建议**，不需要一开始开发复杂的机器学习推荐系统。

示例规则：
- 某个错误类别在最近若干次练习中反复出现：增加相关练习。
- 某个错误连续多次未出现且有足够样本：降低该主题的复习频率。
- 用户连续多次完成当前难度的练习，且反馈显示表现稳定：建议尝试更高难度。
- 用户连续多次难以完成当前任务：建议保持或降低难度，并提供更多提示。
- 数据不足：维持当前难度，提示系统仍在收集练习数据。

具体阈值应放在配置或独立规则模块中，不要散落在多个 UI 文件里。初始阈值需要通过实际测试逐步调整，不得宣称这些规则已被科学验证。

## 8.5 进步结果如何呈现

可以呈现：
- 已完成练习次数。
- 累计练习时长。
- 常见错误类别的出现次数变化。
- 复习任务完成情况。
- 练习连续性。
- 不同训练主题的完成情况。
- 有足够样本时的趋势图。

必须遵守：
- 每项指标都应有明确计算方法。
- 展示时间范围，例如最近 7 天或最近 30 天。
- 区分事实统计、AI 反馈和估计值。
- 样本不足时显示「数据不足」，不展示虚假的进步百分比。
- 不把模型生成的主观评价包装成精确、客观的能力分数。
- 如展示 IELTS / TOEFL 估计分数，必须标记为非官方 AI 估计。

## 8.6 用户可控性

- 用户可修改学习目标、英语水平和偏好。
- 系统推荐不能阻止用户自由选择练习主题。
- 用户可查看推荐原因，例如「最近几次练习中，过去时错误出现较多」。
- 用户可以跳过或拒绝推荐。
- 用户可以删除历史练习数据；删除后应按规则重新计算相关学习指标，或清楚标注历史数据不完整。

# 10. 面向未来 App 的 API-first 架构

## 10.1 核心要求

第一阶段只开发 Web，但不能把核心业务写成只能由网页组件调用的逻辑。未来 App 应能够通过同一套后端 API 实现相同的口语训练、历史记录和学习进度功能。

## 10.2 建议的技术架构

可根据当前项目情况调整，但优先考虑：

- **前端：** Next.js + TypeScript。
- **UI 样式：** Tailwind CSS 或项目中已存在的等效方案。
- **服务端：** Next.js Route Handlers / Server Actions 中清晰分层的服务端 API；需要时再拆分独立后端。
- **数据库：** PostgreSQL；可评估 Supabase。
- **用户认证：** 采用与数据库和部署方案兼容的认证服务。
- **AI：** DeepSeek API，通过服务端 Provider 封装。
- **语音识别与合成：** 独立 Provider 接口，供应商在验证后确定。
- **部署：** 根据服务在目标地区的可用性、网络、成本和 API 访问情况选择。

不要仅为“以后可能做 App”就过早拆成微服务。当前以一个结构清楚、可维护的全栈项目为主，但要保持 API 与 UI 的边界。

## 10.3 API 设计原则

- 统一使用 `/api/v1/` 作为业务 API 的版本前缀。
- 返回统一的 JSON 格式。
- 对受保护接口进行身份认证和权限检查。
- 对输入参数进行服务端验证。
- 对外部 AI API 设置超时与错误处理。
- 重要写入操作避免重复执行造成重复记录。
- 不向客户端返回密钥、内部堆栈或敏感信息。
- 保持响应结构稳定，以便未来 App 使用。
- 为 API 编写基本文档和测试。

## 10.4 初步 API 清单

实际路径可以根据项目约定调整，但应覆盖以下能力：

| 方法 | 路径示例 | 用途 |
|---|---|---|
| `GET` | `/api/v1/me` | 获取当前用户资料 |
| `PATCH` | `/api/v1/me` | 更新用户偏好 |
| `POST` | `/api/v1/practice-sessions` | 创建练习会话 |
| `GET` | `/api/v1/practice-sessions` | 获取当前用户的练习列表 |
| `GET` | `/api/v1/practice-sessions/:id` | 获取某次练习详情 |
| `POST` | `/api/v1/practice-sessions/:id/messages` | 提交一条消息并获取 AI 回复 |
| `POST` | `/api/v1/practice-sessions/:id/finish` | 结束练习并生成总结 |
| `GET` | `/api/v1/practice-sessions/:id/summary` | 获取练习总结 |
| `GET` | `/api/v1/learning/progress` | 获取学习进度 |
| `GET` | `/api/v1/learning/reviews` | 获取待复习内容 |
| `POST` | `/api/v1/learning/reviews/:id/complete` | 标记复习完成 |
| `GET` | `/api/v1/learning/recommendations` | 获取下一次训练建议 |
| `DELETE` | `/api/v1/practice-sessions/:id` | 删除用户自己的练习记录 |

接口清单是规划，不代表必须一次全部实现。应先实现当前阶段所需的最小集合。

# 11. 安全、隐私与可靠性

必须实现或规划以下措施：

- API Key 仅在服务端保存。
- 提供 `.env.example`，真实 `.env` 加入 `.gitignore`。
- 用户只能访问自己的资料和学习记录。
- 服务端校验所有关键输入。
- 登录与受保护 API 具备认证和授权。
- 处理请求超时、限流、断网和第三方服务错误。
- 防止重复提交导致同一消息或总结被重复保存。
- 对 AI 输出进行结构验证，不能盲目信任模型结果。
- 不默认保存原始语音。
- 为用户提供删除练习记录的方式。
- 记录必要的运行日志，但不记录密钥、认证令牌或不必要的个人数据。
- 正式上线前检查依赖漏洞、环境变量、数据库权限和错误页面。
- 对费用较高或可能被滥用的 AI 请求设置合理的请求限制与用量监控。

# 15. 建议的环境变量

实际变量名应与所选服务和框架保持一致。可从以下清单开始：

```env
# DeepSeek（只允许服务端读取）
DEEPSEEK_API_KEY=
DEEPSEEK_MODEL=

# 数据库 / 认证服务（根据最终选型填写）
DATABASE_URL=
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=

# 语音服务（供应商确定后再增加）
SPEECH_TO_TEXT_PROVIDER=
SPEECH_TO_TEXT_API_KEY=
TEXT_TO_SPEECH_PROVIDER=
TEXT_TO_SPEECH_API_KEY=

# 应用环境
NEXT_PUBLIC_APP_NAME=SpeakMate AI
```

重要说明：
- 此处变量仅为配置规划，具体是否全部使用取决于最终技术选型。
- `NEXT_PUBLIC_` 前缀的变量会暴露给浏览器，因此不得给需要保密的密钥使用此前缀。
- `SUPABASE_SERVICE_ROLE_KEY` 等高权限密钥只能在服务端使用。
- 如果使用托管平台的数据库连接方式，应按官方推荐的连接与连接池配置。
- 真实 `.env` 文件必须加入 `.gitignore`。
